# Migration guide: Access Management sync and configuration refactor

This migration syncs the app's metadata, routes and menus with the IGRP Access Management API, and splits the template configuration into helper functions.

## Access Management synchronization

At startup the app now registers its metadata, routes and menus in Access Management, so they no longer have to be configured there by hand.

### 1. Route synchronization (`packages/framework/next/src/lib/sync-routes.ts`)

`igrpSyncRoutes()` registers the app's static routes as Access Management resources, where they can then be assigned to menus and used for resource-based access control.

```typescript
export async function igrpSyncRoutes({
  baseUrl,
  m2mServiceId,
  m2mToken,
  appRoutes,
  paramMapBody,
}: IGRPSyncRoutesArgs)
```

It parses the `ParamMap` interface from the Next.js route type definitions and keeps only static routes (routes without parameters). It leaves out the system routes `/login`, `/logout` and `/[...not-found]`, builds a `ResourceDTO` with one item per route, and sends it to the Access Management API with M2M authentication.

### 2. Menu synchronization (`packages/framework/next/src/lib/sync-menus.ts`)

`igrpSyncMenus()` sends the menus defined in code to Access Management, for the given application code, keeping their structure and hierarchy.

```typescript
export async function igrpSyncMenus({
  appCode,
  menus,
  baseUrl,
  m2mServiceId,
  m2mToken,
  syncEnabled,
}: IGRPSyncMenusArgs)
```

It runs only when `IGRP_SYNC_ON_CODE_MENUS` is enabled, so it can stay off in production. It maps the IGRP menu types to the Access Management API types and logs the sync status.

### 3. Application synchronization (`packages/framework/next/src/lib/sync-application.ts`)

`igrpSyncApplication()` creates or updates the application in Access Management from the name, description and version in `package.json`.

```typescript
export async function igrpSyncApplication({
  appInformation,
  baseUrl,
  appCode,
  m2mServiceId,
  m2mToken,
}: IGRPSyncApplicationArgs)
```

It builds an `ApplicationDTO`, generates an application code when none is given, and sets the type to `INTERNAL` and the status to `ACTIVE`.

### 4. Startup sync orchestration (`packages/framework/next/src/lib/startup-sync.ts`)

`igrpStartupSync()` is the single entry point for all sync operations.

```typescript
export async function igrpStartupSync({
  syncEnabled,
  appInformation,
  baseUrl,
  appCode,
  m2mServiceId,
  m2mToken,
  menus,
  appRoutes,
  paramMapBody,
}: IGRPStartupSyncArgs)
```

It does nothing unless `IGRP_SYNC_ACCESS` is enabled. A singleton makes sure it runs once per application instance. It syncs in this order:

1. Application metadata
2. Routes
3. Menus

Each step is logged. A failed sync is logged and does not stop the application from starting.

### 5. Integration in the root layout (`packages/framework/next/src/layouts/igrp-root-layout.tsx`)

The root layout calls `igrpStartupSync()` before the page renders, with the sync settings from `apiManagementConfig` in the template config and the sidebar menu items.

```typescript
await igrpStartupSync({
  syncEnabled: syncAccess,
  appInformation,
  baseUrl: apiManagementConfig?.baseUrl || '',
  appCode,
  menus: sidebarData.menuItems || [],
  m2mServiceId: apiManagementConfig?.m2mServiceId || '',
  m2mToken: apiManagementConfig?.m2mToken || '',
  appRoutes: apiManagementConfig?.appRoutes,
  paramMapBody: apiManagementConfig?.paramMapBody,
});
```

## Configuration refactoring

### Template configuration (`src/igrp.template.config.ts`)

The configuration used to be inline: it read environment variables directly, hardcoded the session arguments and extracted no routes. It now calls the helpers in `lib/config/`, so each piece can be tested on its own, and it adds an `apiManagementConfig` section with the extracted routes.

```typescript
import { getPackageJson } from "./lib/config/get-pkj";
import { getSessionArgs } from "./lib/config/get-session-args";
import { getRoutes } from "./lib/config/get-routes";

// ...

const routes = getRoutes();
const appRoutes = routes?.appRoutes ?? [];
const paramMapBody = routes?.paramMapBody ?? "";

// ...

apiManagementConfig: {
  baseUrl: process.env.IGRP_ACCESS_MANAGEMENT_API || "",
  m2mServiceId: process.env.IGRP_M2M_SERVICE_ID || "",
  m2mToken: process.env.IGRP_M2M_TOKEN || "",
  syncOnCodeMenus: process.env.IGRP_SYNC_ON_CODE_MENUS === "true",
  appRoutes,
  paramMapBody,
},
sessionArgs: getSessionArgs(),
```

## New helper functions

### 1. Package JSON (`src/lib/config/get-pkj.ts`)

Returns the name, version and description from `package.json` as an `IGRPPackageJson`. `igrp.template.config.ts` passes it as `appInformation`, which the application sync uses.

```typescript
export function getPackageJson() {
  const appInfo: IGRPPackageJson = {
    name: pkg.name,
    version: pkg.version,
    description: pkg.description,
  };
  return appInfo;
}
```

### 2. Session arguments (`src/lib/config/get-session-args.ts`)

Holds the session configuration in one place. In preview mode it turns session refetching off; otherwise it polls every five minutes and on window focus. Both branches normalize the auth base path.

```typescript
export function getSessionArgs() {
  if (isPreviewMode()) {
    return {
      refetchInterval: 0,
      refetchOnWindowFocus: false,
      basePath: getBasePath(process.env.NEXT_PUBLIC_BASE_PATH || ""),
    };
  }

  return {
    refetchInterval: 5 * 60,
    refetchOnWindowFocus: true,
    basePath: getBasePath(process.env.NEXT_PUBLIC_BASE_PATH || ""),
  };
}
```

### 3. Route extraction (`src/lib/config/get-routes.ts`)

Reads the routes type file that Next.js generates for the App Router (`.next/types/routes.d.ts`) and returns the routes array and the `ParamMap` body, so routes no longer have to be listed by hand.

```typescript
export function getRoutes() { 
  try {
    const file = path.join(process.cwd(), ".next/types/routes.d.ts");
    const content = fs.readFileSync(file, "utf8");

    const appRoutesMatch = content.match(/type AppRoutes\s*=\s*([\s\S]*?)\n(?=type|interface)/);
    const paramMapMatch = content.match(/interface ParamMap\s*{([\s\S]*?)^}/m);

    // ... parsing logic ...

    return { appRoutes, paramMapBody };
  } catch (error) {
    console.warn("Could not read routes file:", error);
  }  
}
```

It extracts the `AppRoutes` union type and the `ParamMap` interface body, parses the routes and drops empty values. If the file cannot be read it logs a warning and returns nothing.

### 4. Base path (`src/lib/config/get-base-path.ts`)

Builds the authentication endpoint path from the base path.

```typescript
export function getBasePath(bp: string) {
  if (!bp) return "/api/auth";

  const normalized = bp.startsWith("/") ? bp : `/${bp}`;
  const cleanPath = normalized.endsWith("/")
    ? normalized.slice(0, -1)
    : normalized;
  return `${cleanPath}/api/auth`;
}
```

An empty base path gives `/api/auth`. Otherwise it adds a leading slash if missing, removes a trailing one, and appends `/api/auth`.

## Template configuration updates

`src/igrp.template.config.ts` gains three sections.

1. Sync switch:
   ```typescript
   syncAccess: process.env.IGRP_SYNC_ACCESS === "true",
   ```

2. API management:
   ```typescript
   apiManagementConfig: {
     baseUrl: process.env.IGRP_ACCESS_MANAGEMENT_API || "",
     m2mServiceId: process.env.IGRP_M2M_SERVICE_ID || "",
     m2mToken: process.env.IGRP_M2M_TOKEN || "",
     syncOnCodeMenus: process.env.IGRP_SYNC_ON_CODE_MENUS === "true",
     appRoutes,
     paramMapBody,
   },
   ```

3. Session arguments:
   ```typescript
   sessionArgs: getSessionArgs(),
   ```

The file extracts the routes from the Next.js types, reads `package.json`, gets the session arguments (with preview mode handling), builds the configuration and passes it to `igrpBuildConfig()`.

## Environment variables

| Variable | Description | Example / values | Required |
|---|---|---|---|
| `IGRP_ACCESS_MANAGEMENT_API` | Base URL for the Access Management API | `https://api.igrp.cv/access-management` | Yes, if sync is enabled |
| `IGRP_M2M_SERVICE_ID` | Machine-to-machine service identifier for API authentication | `my-app-service` | Yes, if sync is enabled |
| `IGRP_M2M_TOKEN` | Machine-to-machine authentication token | `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...` | Yes, if sync is enabled |
| `IGRP_SYNC_ACCESS` | Enables Access Management synchronization | `true` / `false` (default `false`) | No |
| `IGRP_SYNC_ON_CODE_MENUS` | Enables menu synchronization from code; only works when `IGRP_SYNC_ACCESS=true` | `true` / `false` (default `false`) | No |

## Migration steps

### Enable Access Management synchronization

1. Set the required environment variables:
   ```bash
   IGRP_ACCESS_MANAGEMENT_API=https://api.igrp.cv/access-management
   IGRP_M2M_SERVICE_ID=your-service-id
   IGRP_M2M_TOKEN=your-m2m-token
   IGRP_SYNC_ACCESS=true
   ```

2. Optionally, enable menu synchronization:
   ```bash
   IGRP_SYNC_ON_CODE_MENUS=true
   ```

3. Restart the development server:
   ```bash
   pnpm dev
   ```

4. Check the console logs for the sync status, then check in Access Management that the application and its routes are registered and, if enabled, the menus are synced.

### Disable synchronization

1. Set the variable to `false`, or remove it:
   ```bash
   IGRP_SYNC_ACCESS=false
   ```

2. Restart the development server.

3. Check that the console shows no sync logs and the application runs normally.

## Testing

### Synchronization

1. Set `IGRP_SYNC_ACCESS=true` and the M2M credentials, then start the application.
2. Check the logs for "IGRP STARTUP SYNC" and for the success message of each sync operation.
3. Log in to the Access Management UI and check that the application is registered, the routes are available and, if enabled, the menus are synced.
4. Start with invalid credentials and check that the error is logged and the application still starts.

### Configuration

1. Preview mode: set `IGRP_PREVIEW_MODE=true`, then check that session refetching is off and the base path is correct.
2. Route extraction: add routes in the app directory, then check that they are extracted and `ParamMap` is parsed.
3. Base path: try several base path formats, including an empty one, and check the normalized result.
