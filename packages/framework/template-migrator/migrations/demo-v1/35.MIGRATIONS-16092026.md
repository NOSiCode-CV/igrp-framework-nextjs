# 35 — The framework owns the post-login redirect, and the session poll gets a ceiling

Two changes, both removing a footgun this template had been working around.

## 1. `src/lib/auth.ts` drops its `callbacks.redirect` override

The template carried its own post-auth redirect callback, with a comment saying
the framework default was *"broken when NEXTAUTH_URL includes `/api/auth`"*. It
was right. `@igrp/framework-next-auth` built the post-login destination by
string-concatenating `NEXTAUTH_URL_INTERNAL` with the app home slug — so with the
`NEXTAUTH_URL` shape NextAuth v4 requires under a `basePath`
(`https://host/apps/template/api/auth`), a sign-in with no `callbackUrl` landed
the browser on the **NextAuth API root** rather than the app home.

That is now fixed upstream. The framework default:

- resolves every destination against the app base URL (`baseUrl` / `NEXTAUTH_URL`
  with the `/api/auth` suffix stripped);
- never uses `NEXTAUTH_URL_INTERNAL` for anything that becomes a `Location`
  header — that variable names a *server-reachable* origin, which in the
  deployments that set it is by definition not reachable from the browser;
- sends the auth chrome (`/login`, `/logout`) to home instead of bouncing the
  user back through the flow they just completed;
- keeps the same open-redirect guards (protocol-relative, backslash, control
  characters, segment-wise `..`).

That is exactly what the local override did, so it becomes dead weight. Deleting
it means the behaviour tracks the framework instead of drifting from it.

`deriveAppBaseUrl()` and `AUTH_UI_PATH` go with it; nothing else referenced them.

### If you customised `src/lib/auth.ts`

This step **replaces** the file, and it is one apps commonly edit (custom
`onSessionExpired`, extra callbacks, provider overrides). Diff your version
against the payload first and re-apply your changes afterwards. If you have your
own `redirect` callback that does something the framework's does not, keep it —
`withIGRPAuth` still honours a caller-supplied `callbacks.redirect` and gives it
full control.

## 2. `IGRP_SESSION_REFETCH_INTERVAL` drops to 45s

The template shipped `120`. The framework's proactive-refresh buffer is **60s**:
the `jwt` callback only refreshes once the access token is within 60s of expiry.
A poll interval at or above that buffer can never land inside the refresh
window — so the only refreshes that run happen during RSC renders, where
`cookies()` is read-only and the rotated token cannot be persisted. The session
then dies in a gap the user experiences as a random bounce to `/login`, with
nothing in the logs tying it to the poll interval.

The constraint had been written down in the framework for a while but never
enforced. `withIGRPAuth` now warns once in development when the value is 60 or
above, so a misconfigured app says so at startup.

`45` leaves ~15s of margin for jitter and request duration. Against this
template's ~180s access token, polls land at 45/90/135s — the one at 135s is
inside the refresh window and persists the rotated cookie well before the
middleware bounce at ~167s.

### Impact on your app

- **If you never set the key**, you were on the framework default of `180` —
  also above the ceiling. You now get an explicit `45`.
- **If you tuned it deliberately above 60**, this migration overwrites it. Set it
  back only if you have also raised the framework's refresh buffer; otherwise you
  are re-opening the gap.
- The key is re-appended at the end of your `.env` (the `env.add` step writes
  fresh), so its position in the file may change. Its value and documentation are
  what matter.
