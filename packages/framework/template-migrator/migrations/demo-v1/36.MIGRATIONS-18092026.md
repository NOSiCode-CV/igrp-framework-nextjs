# 36 — Middleware redirects resolve through the framework, not `request.url`

`src/middleware.ts` built its three redirects with `new URL(path, request.url)`.
Behind a TLS-terminating proxy, `request.url` is the **internal** origin the pod
was reached on (`http://pod:3000/…`), not the origin the browser is using — so a
`Location` built from it points somewhere the browser cannot follow.

All three now go through the framework's single resolver:

| Before | After |
| --- | --- |
| `new URL(`${BASE_PATH}/login`, request.url)` | `auth.getLoginRedirectUrl(request)` |
| `new URL(`${BASE_PATH}/`, request.url)` | `auth.resolveAppUrl("/", request)` |

`resolveAppUrl` prefers `NEXTAUTH_URL` (minus the `/api/auth` suffix v4 requires
under a basePath), recovers the basePath from it when `NEXT_PUBLIC_BASE_PATH` is
unset, and falls back to the request origin when `NEXTAUTH_URL` is absent. It
never consults `NEXTAUTH_URL_INTERNAL` — that variable names a server-to-server
origin by definition and must not reach a `Location` header.

## Why this is a migration and not just a refactor

There were two implementations of "where is this app, really": the framework's
and this one. They agreed whenever `NEXTAUTH_URL`'s origin matched the request
origin — i.e. everywhere except the deployment shape that motivated
`NEXTAUTH_URL_INTERNAL` in the first place. Collapsing them to one removes a
class of proxy-only redirect bug rather than a few lines of duplication.

## Impact on your app

- **Single-host / local development is unchanged.** `NEXTAUTH_URL` and the
  request origin are the same there, so every redirect resolves identically.
- **Behind a proxy, login redirects now target the public origin.** If you were
  relying on the internal origin leaking into a redirect, that stops.
- **If `NEXTAUTH_URL` is unset**, behaviour is exactly as before — the resolver
  falls back to the request origin.
