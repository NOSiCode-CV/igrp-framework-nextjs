# 40 — review hardening: dead env var, silent route parse, double config build

A full review of `templates/demo-v1` on 2026-09-22. Nine files change; none of
them alters runtime behaviour except where called out below.

## `.env.example` — `IGRP_SESSION_REFETCH_INTERVAL` removed (again)

Migration 19 removed this variable when `IGRPSessionWatcher` took over adaptive
refresh. It came back, with a long doc block asserting a **hard ceiling of 60s**
and instructing you to set it explicitly.

Nothing reads it.

- `src/lib/config/get-session-args.ts` returns a hardcoded 600s backstop and
  never looks at the env.
- The only reader anywhere in the framework is
  `warnOnRefetchIntervalMisconfiguration` in `@igrp/framework-next-auth`, which
  **warns and nothing else**.

So the guard inspected `45` (the documented value), passed, and stayed quiet —
while the value that actually reached `SessionProvider` was `600`, ten times past
the ceiling the guard exists to enforce. A guard that reads a variable with no
effect on the thing it guards cannot ever fire correctly. This is the same shape
as the three silent-no-op guards recorded in the repo's `KNOWN-ISSUES.md`.

The 600s backstop is **correct** — `IGRPSessionWatcher` schedules the real
refresh from `session.expiresAt`, so the fixed poll is only a last resort. Only
the documentation was wrong. A replacement note now states that the absence of
this knob is deliberate, so it does not return a third time.

**No action needed in your `.env`** — a leftover `IGRP_SESSION_REFETCH_INTERVAL`
there is inert. Delete it for tidiness.

## `src/lib/config/get-routes.ts` — the silent-empty path is now loud

This file regex-parses `.next/types/routes.d.ts`, a Next.js internal with no
stability guarantee. On any failure it returned `undefined`, which became
`appRoutes: []` in `apiManagementConfig` — Access Management's resource/route
sync then registered **nothing**, with one `console.warn` as the only trace.

```diff
-  } catch (error) {
-    console.warn("Could not read routes file:", error);
-  }
+  console.error(
+    "[get-routes] routes.d.ts parsed to nothing — its format changed … " +
+      "Access Management will receive ZERO app routes, so resource/route sync " +
+      "registers nothing.",
+  );
```

Three changes:

1. Read failure and parse failure are reported separately, each naming the
   consequence rather than the symptom.
2. **The parse asserts it did some work** — a match that yields zero routes is
   treated as a failure, not as "no routes". A guard that can pass while
   checking nothing is not a guard.
3. The **miss is cached**. Previously only the success path was cached, so every
   render after a failure paid another synchronous `readFileSync` and logged
   again.

The runtime read itself stays: unlike `.igrpstudio/permissions.json`, this file
does not exist until Next has generated types for the very build that would
bundle it. `.next/types/` **is** included in `output: "standalone"`, so the
container has it.

## `src/igrp.template.config.ts` — config is built once per request

`app/layout.tsx` and `app/(igrp)/layout.tsx` both call `createConfig`. It was not
memoized, so `igrpBuildConfig` — plus `getRoutes()` (a synchronous file read),
`getPermissions()` and `getSessionArgs()` — ran **twice per request**, producing
two distinct config objects for one render.

```diff
-export const createConfig: IGRPConfigClient = (config) => { … };
+const buildConfig: IGRPConfigClient = (config) => { … };
+export const createConfig: IGRPConfigClient = cache(buildConfig);
```

`cache()` keys on argument identity, and the sole argument comes from
`getLayoutConfig` in `lib/dal.ts`, which is itself `cache()`d — so both layouts
pass the same object and share one result. This makes it *provable* that the root
layout and the authenticated layout see identical config, rather than merely
likely.

## `src/middleware.ts` — `X-XSS-Protection: 0`

```diff
-  "X-XSS-Protection": "1; mode=block",
+  "X-XSS-Protection": "0",
```

The legacy XSS Auditor this header controls has been removed from every current
browser, and where it survives its filtering has itself been an XSS vector.
Explicitly disabling it is current OWASP and Chrome guidance. The real defence is
the CSP already in this file.

The dotted-path branch in `isPublicPath` also gains a comment: under the stock
`auth.config` matcher (which excludes `.*\..*`) it never runs, and it is **not**
the auth boundary for dotted page routes — those are protected because
`(igrp)/layout.tsx` calls `verifySession()`. Don't move a protected route out
from under that layout assuming middleware covers it.

## `tsconfig.json` — `noEmit: true`, `composite` dropped

`noEmit: false` plus `composite: true` meant a bare `tsc -p .` emitted compiled
`.js` next to every source file. Next.js owns compilation here; `tsc` is only
ever used to type-check, nothing references this project, and `tsc -b` is never
run against it. This is the same hazard the repo-root `tsconfig.json` documents
for the projects that emit via something other than `tsc`.

## `src/app/(auth)/login/page.tsx` — redundant classes

`cn()` was passed `hidden` twice and `lg:block` on top of `md:block`. Rendering is
unchanged (tailwind-merge already collapsed them); the class list now says what
it means.

## Permission decisions are now stated on every page

`.agents/rules/permissions.md` requires each page to either gate on a permission
or carry a one-line comment saying it is deliberately open. Only one of the
template's own pages did. Every page under `(igrp)` now states its decision, so
`grep` over the tree distinguishes "open on purpose" from "nobody thought about
it".

`src/app/(igrp)/page.tsx` is the only one of these that is migration-managed and
therefore ships here; the rest are demo scaffolding that a real app deletes, so
they reach you through the zip only.

The comments deliberately **do not name the guard function**. Auditing which
pages are gated is a grep for the call, and a mention in prose defeats it — the
first draft of this change named it and produced three false positives on pages
that are not gated at all.

## `src/lib/header-search.ts` — formatting only

Reformatted to Biome's 80-column width. It and `src/igrp.template.config.ts` were
the only two CRLF files in the template, which made `biome check --write` (part
of `pnpm build`) rewrite them on every build. A repo-root `.gitattributes` now
pins the tree to LF so this cannot recur.

## `cn` comes from the design system, and the design system now has a way to give it

The template used to declare its own `cn` dependency (at `^0.3.0`, the only caret
range in the manifest) and import from it directly. That dependency is **removed**.
`cn` now comes from the design system in both files that use it.

That is only possible because the design system gained a **server-safe entry**,
`@igrp/igrp-framework-react-design-system/cn`, in the same release. Its root
barrel is a `"use client"` boundary, so until now server code simply could not
import `cn` from it:

```
Error: Attempted to call cn() from the server but cn is on the client.
> Build error occurred
[Error: Failed to collect page data for /admin/users]
```

Both call sites in this template are server-side, and they take different routes
out:

- **`src/lib/fonts.ts`** drops `cn` entirely. It joins four `next/font`
  CSS-variable class names — opaque generated identifiers, no Tailwind utility
  among them — so there is nothing for tailwind-merge to resolve. A plain
  `.join(" ")` produces the same string with no import at all. This one mattered
  most: the module is reached from the root layout and calls at **module scope**,
  so it took down every route.
- **`src/app/(auth)/login/page.tsx`** genuinely wants conditional merging, so it
  imports from the new `/cn` subpath.

**Why this is worth a migration rather than a note:** the failure is invisible to
every gate short of a real build. `tsc --noEmit` passes, `biome check` passes,
and the error only appears during Next's page-data collection — *after*
"Compiled successfully" and *after* types validate. It is then attributed to
whichever route happened to pull the root layout in first, which is never the
file at fault.

`.agents/rules/ui.md` now states which entry to use on which side of the
boundary, instead of saying "from the design system" and leaving server code
with no satisfiable option.
