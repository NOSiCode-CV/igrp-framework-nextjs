# 41 — re-capture `query-client.server.ts` after a comment trim

No runtime change. One file, comments only.

## What changed

`templates/demo-v1/src/providers/query-client.server.ts` lost its four-line
doc block:

```ts
// Per-request server-side QueryClient. Memoized with React's cache() so all
// server components in the same request share one instance. Uses the same
// `makeQueryClient` defaults as the client provider so SSR-prefetched queries
// hydrate with matching staleTime/gcTime/retry behaviour.
```

The code is untouched — `export const getQueryClient = cache(() => makeQueryClient())`
is byte-identical to what migration `28-resync-beta165-query-provider-split`
shipped.

## Why this migration exists at all

Because the two delivery channels would otherwise disagree. Migration 28's
payload still carries the comment, so an app upgraded with `igrp-migrate apply`
would keep it while an app scaffolded from the current zip would not. That is
the divergence `check:drift` exists to catch, and it caught this one:

```
✗ 1 file(s) changed in the template but NOT captured in a migration:
    src/providers/query-client.server.ts  (latest migration: 28-resync-beta165-query-provider-split)
```

A comment-only difference is still a real difference: `git diff` after an
upgrade shows churn that has nothing to do with the upgrade, and the template's
own Biome run has one more file to think about. Re-capturing the file into a
fresh payload is the cheap, honest fix — the same pattern every other
re-capture migration in this directory follows.

## Note for whoever reads this later

The comment was accurate. `makeQueryClient` really does set
`staleTime: 30_000`, `gcTime: 5 * 60_000` and `retry: false`, and `cache()`
really does give one instance per request. It was removed as part of a
deliberate trim, not because it had gone stale. If you want the rationale back,
put it in `src/providers/query-client.ts` next to the defaults it describes,
and ship that as its own migration — do not hand-edit `payload/41/`.
