# 56 — Optional Redis session store (`IGRP_SESSION_STORE_URL`)

## What changed

| File | Change |
| --- | --- |
| `package.json` | new dependency `redis` `5.12.1` |
| `src/instrumentation.ts` | new — registers the session store at server start, Node runtime only |
| `src/lib/session-store.ts` | new — Redis implementation of `IGRPSessionStore` |
| `.env.example` | documents `IGRP_SESSION_STORE_URL` |
| `src/lib/header-search.ts` | comment only — points at `AppSearch`'s new path |

Requires `@igrp/framework-next-auth` with the `./session-store` entry, and
`@igrp/framework-next` with the store-aware cookie fallback (the release after
`0.2.0-beta.5` / `0.2.0-beta.6`).

**Opt-in.** Nothing changes until `IGRP_SESSION_STORE_URL` is set: without it,
`register()` returns early and session cookies hold the tokens as before.

## Why

A NextAuth session cookie holds the access, refresh and id tokens: 3–4 KB per
app, more for users with many permissions. Apps that share one domain share the
browser's cookie jar, and an app center at `/` writes its cookie at `Path=/`, so
every request to `/apps/<app>` carries the center's cookie plus the app's own.
On 2026-10-13 that reached 8.2 KB on `demoigrp.nosi.cv` and the ingress
answered `400 Request Header Or Cookie Too Large` for the whole domain.

With the store, the tokens live in Redis (encrypted with `NEXTAUTH_SECRET`) and
the cookie carries only a session id plus the expiry claims middleware checks:
a few hundred bytes, whatever the token size or the number of apps.

## How to enable

1. Point every replica of the app at the same Redis:
   ```env
   IGRP_SESSION_STORE_URL=redis://:password@redis.demo-igrp-stack.svc:6379/0
   ```
2. Restart. Existing sessions keep working and move to the store on their next
   refresh — nobody is signed out.

Turn it on for **every** app on the domain. The app center matters most: its
cookie is the one sent to every app.

## Behaviour to know

- **Redis down:** new sessions are written to the cookie as before (bigger, but
  signed in); sessions already in the store read as signed out and sign in
  again. Every store call is bounded at 2 s.
- **Sign-out** deletes the stored session, so a copied cookie stops working.
- **Middleware** never touches Redis: `instrumentation.ts` registers the store
  in the Node runtime only, and the cookie still carries the expiry the
  middleware checks. `auth.getTokenFromRequest()` therefore returns no
  `accessToken` once the store is on — read tokens server-side
  (`auth.getAccessToken()`), never in middleware.
- **Removing the variable later** signs out every store-backed session once.
