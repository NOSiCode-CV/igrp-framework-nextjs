# 57 — Middleware `matcher` as a literal, so Next actually applies it

## What changed

| File | Change |
| --- | --- |
| `src/middleware.ts` | `export const { config } = auth;` → a literal `export const config = { matcher: [...] }` with the same values |

No environment or dependency changes.

## Why

Next reads the middleware `config` **at build time, by parsing the file**: it
must be an object literal of string literals. `export const { config } = auth`
cannot be parsed, so Next silently ignored it and ran the middleware on **every**
path. The build's `.next/server/middleware-manifest.json` showed the matcher as
`/:path*`.

Nothing broke, because the middleware also skips static paths in code, but every
static asset (`.js`, `.css`, images, fonts) woke the middleware. With the literal,
Next applies the intended matcher: it skips `/apps`, `/_next` and `favicon.ico` as
whole segments, and static assets by extension. Page routes with a dot
(`/users/john.doe`) still go through the middleware.

The values are those of the framework's default matcher (`auth.config.matcher`).
A test in `@igrp/framework-next-auth` keeps the two in sync.

## ⚠️ If you customised this file

`src/middleware.ts` is replaced. If you added matchers, add them to the literal
array: plain strings only, no variables or function calls. Re-apply any other
customisation on top of the new file.

## How to check

After `next build`, `.next/server/middleware-manifest.json` →
`middleware["/"].matchers[].originalSource` should list the three patterns, not
`/:path*`.
