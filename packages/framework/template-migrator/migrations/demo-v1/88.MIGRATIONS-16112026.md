# 88 — A local-only logout no longer signs the user back in

## What changed

| File | Change |
| --- | --- |
| `src/app/(auth)/logout/page.tsx` | Sets the silent sign-in guard cookie (`markSilentSsoTried()`) before every navigation to `/login`. |
| `src/lib/auth.ts` | Drops its own `NEXTAUTH_SECRET` check and hand-written `DYNAMIC_SERVER_USAGE` test, and uses the framework's `isNextControlFlowError` instead. |

## Why

When the IdP's end-session URL could not be fetched (slow or unreachable discovery, or no `end_session_endpoint`), logout cleared only the local session and went to `/login`. `/login` then tried a silent sign-in (`prompt=none`). The IdP session was still alive, so the user was signed straight back in. With an IdP that has no `end_session_endpoint`, every logout was undone this way. The IdP round-trip path already set the guard; the local-only path now does too.

The framework already throws `AUTH_SECRET_MISSING` in production from `auth.serverSession()`, so the template's copy of that check only produced a second warning in development. `isNextControlFlowError` also recognises the other Next.js bailout errors the old digest test missed.

## Behaviour changes to check

- After a local-only logout, `/login` shows the login form instead of trying a silent sign-in. The guard lasts 60 seconds; a later visit to `/login` tries silently again.
- Without `NEXTAUTH_SECRET` in development, you see one warning (the framework's) instead of two.

## After migrating

Nothing to do. If you changed either file, merge by hand:

- `logout/page.tsx`: import `markSilentSsoTried` from `@/lib/silent-sso` and call it inside `hardNavigate`, before `window.location.replace(url)`.
- `lib/auth.ts`: remove the `if (!process.env.NEXTAUTH_SECRET) { … }` block, and replace the `digest === "DYNAMIC_SERVER_USAGE"` check with `if (isNextControlFlowError(error)) throw error;` (imported from `@igrp/framework-next-auth/runtime`).
