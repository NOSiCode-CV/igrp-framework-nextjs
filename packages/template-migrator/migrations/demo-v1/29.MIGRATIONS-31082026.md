# 29 — Permissions catalog sync

Registers the application's **permission catalog** in the central Access
Management (AM) service, so a department manager can bind those permissions to
roles in the AM admin UI.

Requires `@igrp/framework-next` ≥ the release carrying `syncPermissions` /
`onCodePermissions` on `apiManagementConfig` (see that package's CHANGELOG;
`targetFrameworkVersion` is left `null` until the version is published).

## What changes

| Path | Change |
| --- | --- |
| `.igrpstudio/permissions.json` | **New.** The catalog, maintained by iGRP Studio. Ships with the two permissions this template actually gates on (`manage_access`, `delete_invoice`). |
| `src/lib/config/get-permissions.ts` | **New.** Loads the catalog via a **static JSON import** and maps it to `IGRPPermissionCatalogEntry[]`. |
| `src/igrp.template.config.ts` | Passes `syncPermissions` + `onCodePermissions` into `apiManagementConfig`, next to the existing on-code menus block. |
| `.env.example` | Documents `IGRP_SYNC_PERMISSIONS` (default `false`). |
| `package.json` | Dependency resync — see below. |

## Dependency resync

This migration also carries a `deps.bump` for four dependencies that had drifted
in the workspace without ever being captured by a migration, so an app upgraded
through the CLI lands on the same versions a freshly-scaffolded one gets:

| Package | Was pinned | Now |
| --- | --- | --- |
| `next` | 15.5.19 (migration 21) | 15.5.22 |
| `react` | 19.2.7 (migration 21) | 19.2.8 |
| `react-dom` | 19.2.7 (migration 21) | 19.2.8 |
| `@igrp/platform-access-management-client-ts` | 0.2.0-beta.11 (migration 20) | 0.2.0-beta.15 |

The AM client bump is **not** incidental to this migration: `syncPermissions`
does not exist on `M2MClient` in `0.2.0-beta.11`. The other three are patch-level
catch-up and are included so the drift gate reflects reality rather than
accumulating further.

## Behaviour

Off by default. The push only happens when **all three** hold:
`IGRP_SYNC_PERMISSIONS=true`, `IGRP_SYNC_ACCESS=true`, `IGRP_PREVIEW_MODE=false`.
So applying this migration changes nothing until a deployment opts in — which
matters, because the target is a shared central service.

The sync is an **idempotent upsert keyed on `name`**. Permissions removed from
the JSON are **not** deleted in AM (that would break tokens already granting
them) — retire them through the AM admin UI.

## Notes for upgraders

- **Registering a permission does not make it checkable.** AM must still grant
  it to a role, and the user's token must carry the resulting claim. See
  `docs/PERMISSIONS.md` → "The catalog vs the claims".
- **Keep catalog names bare** (`manage_access`, not `DEPT.manage_access`). AM
  qualifies with the department when granting, and the gates match the bare
  suffix against `${org}.${suffix}`. A name *containing a dot* is treated as
  already qualified and matched verbatim, so `igrpAuthorize("invoice.delete")`
  would silently deny against `DEPT.invoice.delete`. The framework warns about
  dotted catalog names off-production.
- A malformed name (anything outside `^[A-Za-z0-9._-]{1,255}$`) is **skipped
  with a warning** rather than blocking boot — this sync is opt-in and
  best-effort.
- The catalog is loaded with a **static import**, not `readFileSync`. A static
  import is traced by the bundler, so the file is present in the Next standalone
  / Docker output; a runtime read of a computed path is not traced and would
  work in dev while being missing in the container.
- If your project has no `.igrpstudio/permissions.json`, the created file is a
  starting point — replace its contents with your own catalog, or leave
  `IGRP_SYNC_PERMISSIONS=false` and it is never read.
