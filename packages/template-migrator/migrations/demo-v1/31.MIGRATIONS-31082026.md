# 31 — Resync to beta.168

A **dependency-only** migration, following directly on migration 30. It touches
no source files and re-pins only the three packages whose versions changed.

## Why a separate migration

Migration 30 shipped in `@igrp/template-migrator@0.1.0-beta.136` and apps have
had the opportunity to apply it. Its recorded `manifestHash` is part of their
lock, so editing it in place would invalidate those locks. New versions
therefore arrive as a new migration rather than an amendment.

## Dependency bumps

| Dependency | Migration 30 pinned | Now |
| --- | --- | --- |
| `@igrp/igrp-framework-react-design-system` | 0.1.0-beta.142 | **0.1.0-beta.143** |
| `@igrp/framework-next-ui` | 0.1.0-beta.163 | **0.1.0-beta.164** |
| `@igrp/framework-next` | 0.1.0-beta.167 | **0.1.0-beta.168** |

Everything else — `@igrp/framework-next-auth`, `@igrp/framework-next-types`,
`@igrp/platform-access-management-client-ts`, `next`, `zod`, `react-hook-form`,
`@tanstack/react-query`, `@types/react-dom` — is unchanged and stays on the
ranges migration 30 set.

## What changed upstream

- **The design system now requires `zod` `^4.5.0`** (was `^4.4.0`), matching the
  range `@igrp/framework-next` already declared. Migration 30 already moved the
  template to `zod@4.5.4`, so an app that applied 30 needs no further action.
  An app that skipped 30 — or removed `zod` from its manifest — must be on
  `4.5.x` before the design system will resolve cleanly.
- `@igrp/framework-next-ui` now pins `react`, `react-dom` and `next-auth` as
  devDependencies so it builds against the same versions as the rest of the
  framework. This is a build-reproducibility fix with no runtime effect on
  consumers.
- `@igrp/framework-next` was bumped by the internal-dependency cascade, not by a
  change of its own: it depends on both packages above, so its pins had to move
  with them.

## Notes for upgraders

- Run your package manager's install afterwards (`pnpm install`). `deps.bump`
  rewrites `package.json` only — it does not touch your lockfile.
- These three versions are designed to move together with the rest of the
  `@igrp/*` set. Apply the whole migration rather than cherry-picking ranges.
