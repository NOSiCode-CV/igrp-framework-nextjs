# 33 — Root layout is `force-dynamic`

Re-captures `src/app/layout.tsx` with a single added line:

```ts
export const dynamic = "force-dynamic";
```

No dependency changes.

## Why

The root layout awaits `getLayoutConfig()`, which resolves the session — and
`src/lib/auth.ts` asserts `NEXTAUTH_SECRET` and the provider env vars while doing
so. Without an explicit segment config, Next tries to **statically prerender**
routes under that layout at `next build` time, so the build itself demands
runtime secrets and fails with:

```
NEXTAUTH_SECRET must be set in production
Missing required authentication environment variables for "igrp-auth"
```

This is a prerender-time failure, not a runtime one. It surfaces most often in
container builds (`docker/development/Dockerfile`, where the image is built
without production secrets), but it applies to any CI that runs `next build`
without a full auth environment.

`force-dynamic` on the root layout marks the whole tree as request-rendered, so
nothing that reads the session is prerendered and the build no longer needs
secrets. This is the correct posture for the template: every page below the root
layout already depends on per-request session and layout data, so none of them
were meaningfully static to begin with.

## Impact on your app

- **No behaviour change at runtime.** The template's pages were already
  effectively dynamic (session + layout data are fetched per request).
- **Builds stop requiring runtime secrets.** If your CI or Dockerfile was
  passing dummy `NEXTAUTH_SECRET` / provider values purely to get `next build`
  through, you can drop them.
- If you deliberately want a *statically* prerendered public route, put it
  outside the session-reading layout tree and give that segment its own
  `dynamic` setting — do not remove this line from the root layout.
